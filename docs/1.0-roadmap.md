# Roadmap to 1.0

This fork was brought to production-ready state in a series of phases
(rebranding, hygiene, Docker/security, selftest + types + e2e, hardening and
docs). This document records what "1.0" means for this project, what has
already landed, and what is deliberately deferred.

## What is in place at 0.10.x

- **Publishing**: npm packages (`@lifestyle3nergy-web/firefox-devtools-mcp`
  and `-moz`) with declaration files, npm trusted publishing (or token
  fallback), provenance, and a fully automated release pipeline
  (version-check → release → publish → GHCR image).
- **Docker**: production-ready image (Mozilla APT repo, build-time Firefox
  version gate, non-root user) with `--selftest` as the health check and
  CI-verified image builds.
- **Testing**: 650+ unit tests, integration suite (including a protocol-level
  e2e test driving the built server over stdio and a process-leak guard),
  real coverage thresholds, cross-OS CI matrix (ubuntu + windows),
  production dependency audit gate, dependabot.
- **Operations**: runbook (`docs/operations.md`), default output capture with
  rotation, security model documented (`SECURITY.md`, including the localhost
  trust model), CI/release documentation kept in sync.

## 1.0 criteria

The API (CLI flags, MCP tool names/schemas, package entry points) is stable
when:

1. **Tool surface is frozen.** Tool names, input schemas, and response shapes
   change only with a major version. (The registry/e2e drift test protects
   against accidental renames.)
2. **CLI is frozen.** Flags are added, not removed or repurposed. Deprecated
   flags (`--enable-script`, `--enable-privileged-context`) must be removed
   or promoted before 1.0 — decide explicitly.
3. **Semver discipline is proven.** At least one minor release cycle where
   `npx ...@^0.x` consumers were not broken, with `bump-version.mjs` and the
   release pipeline used for every release.
4. **The e2e suite passes on all supported platforms** in CI for several
   consecutive releases without changes.

## Deferred (with reasons)

| Item | Why deferred | Revisit when |
| --- | --- | --- |
| Container image signing (cosign/sigstore) | No in-house verification path yet; provenance (npm) + GHCR digest pinning covers most of the risk for now | When image consumers can verify signatures (e.g. an internal sigstore or GHCR attestations workflow) |
| Soak / long-running load test | Valuable but orthogonal to correctness; a dedicated harness (hours of tab churn + BiDi traffic) does not belong in the PR-sized CI budget | Dedicated nightly workflow, after the process-leak guard has been clean in CI for a while |
| macOS in the CI matrix | Known Firefox-startup crash on the runner is upstream/Firefox-side, not in this codebase | Upstream fix lands in the Firefox version CI installs |
| Hard Codecov CI gate | Coverage is already gated by vitest thresholds on every run; a second opinion gate that can fail on missing tokens is net-negative for forks | If Codecov becomes the canonical coverage store (token configured) |
